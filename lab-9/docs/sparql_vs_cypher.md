|---|---|---|

## 3. Text-to-Cypher (C3, C4)
Реалізація `t2c/t2c.py`: схема у підказці (`t2c/schema_prompt.txt`) → LLM → валідатор (заборонені ключові слова, невідомі мітки/зв'язки,
один оператор, обов'язковий LIMIT) → виконання у READ-транзакції (сервер відхиляє запис) → порівняння з еталоном із `tests/t2c.jsonl`.

> Про «read-only роль»: Neo4j Community Edition не має користувацьких ролей (RBAC — функція Enterprise). Тому read-only забезпечено на двох рівнях:
> (1) драйвер відкриває транзакцію в режимі READ — сервер відхиляє запис; (2) валідатор до виконання блокує запис/CALL/LOAD CSV.
> У звіті прямо напишіть це; з Enterprise-ліцензією можна додатково створити роль із лише `MATCH`-привілеєм.

**Метрика:** частка коректних = `correct / N` (N = 12 запитань + 2 негативні тести безпеки s01–s02, де «правильно» = відхилено).
Результат: _…/14 = …%_ (з виводу `t2c.py`).

**Аналіз 3 помилок (C4)** — з файлу `tests/t2c_results_*.jsonl` та `llm_log/t2c_*.jsonl`:

| id | питання | що згенерував LLM | категорія (unknown_label / wrong_result / execution_error / …) | причина | як виправити підказку |
|---|---|---|---|---|---|
| | | | | | |

**Ризики text-to-Cypher і як зменшені (для захисту, питання 5):** ін'єкція/запис (READ-режим + чорний список), галюцинація схеми (перевірка міток/зв'язків проти `db.labels()`),
дорогі запити (LIMIT), неправильна семантика, що виглядає правдоподібно (порівняння з еталоном; людина перевіряє), витік даних (ключ API лише у змінній середовища, у зовнішній сервіс (Gemini, безкоштовний рівень може використовувати запити для покращення продуктів) іде лише питання+схема, без даних).
