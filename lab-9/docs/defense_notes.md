# Підготовка до захисту (5 питань × 0.1 бала; потрібно пояснити «живцем» і змінити запит)

**1. LPG vs RDF.** RDF — набір тріплетів (суб'єкт–предикат–об'єкт) з глобальними IRI, стандарти W3C, SPARQL, OWL-виведення, SHACL; добре для обміну/інтеграції й семантики.
LPG — вузли й ребра, на яких *прямо* лежать властивості (у т.ч. `source`, `confidence` на ребрі); добре для навігації шляхами, аналітики графа (PageRank, спільноти) та застосунків.
Мій вибір: RDF — коли потрібні стандартні словники, виведення, федерація; LPG — коли потрібні швидкі обходи, властивості на зв'язках і GDS. Тут: провенанс на ребрах і GDS → LPG; семантика/валідація (класи, reasoner, SHACL) → RDF з ЛР 8.

**2. Поясніть свій запит.** Розберіть Q4 по рядках: `MATCH (al:Airline)<-[:OPERATED_BY]-(f:Flight)` — знайти рейси й їхню компанію; `OPTIONAL MATCH (f)-[:HAS_DELAY]->(d)` — як LEFT JOIN: рейс без затримки лишається, `d = null`;
`count(DISTINCT f)` — усі рейси; `count(d)` — лише не-null, тобто затримані; `sum(d.minutes)` — null ігноруються, `coalesce(...,0)` дає 0 для компаній без затримок.
Групування неявне: усі непід'єднані до агрегатів вирази в RETURN (тут `al.name`) — ключ групування.
Для «наживо»: вміти змінити поріг у Q6, дату в Q1, глибину `*1..3` у Q2, аеропорт у Q13.

**3. Обмеження й індекси.** UNIQUE-обмеження гарантує відсутність дублікатів ключа і автоматично створює індекс; без нього `MERGE` міг би створити дублі й повільно шукав би вузол.
Індекс прискорює пошук за властивістю (NodeIndexSeek замість NodeByLabelScan). Перевірка: `SHOW CONSTRAINTS/INDEXES`, спроба створити дубль (помилка), `PROFILE` до/після (db hits).

**4. PageRank / Louvain.** PageRank — «важливість» аеропорту за кількістю й вагою вхідних маршрутів від важливих вузлів: хаби (LWO, WAW, FRA…) — критичні точки мережі.
Louvain — спільноти з найбільшою модулярністю: регіональні кластери маршрутів навколо хабів компаній; ізольовані аеропорти — окремі спільноти (прогалини даних).
Користь для знань: де концентрувати моніторинг ризиків, які частини графа можна верифікувати/підтримувати окремо.

**5. Ризики text-to-Cypher.** Запис/видалення даних (READ-транзакція + чорний список), вигадані мітки/зв'язки (перевірка проти `db.labels()`/`db.relationshipTypes()`),
важкі запити (LIMIT), правдоподібно-неправильна семантика (порівняння з еталоном, перегляд людиною), витік даних/ключів (ключ лише в env, у LLM (Gemini) іде схема+питання, не дані).
Обмеження: Community без RBAC → read-only емульовано.
