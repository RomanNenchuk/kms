# Результат 1. Рекомендаційний модуль: проєктні рішення

Предметна область: управління авіаційними перевезеннями. Задача: рекомендувати користувачам Hub (диспетчер, аналітик, менеджер операцій, планувальник ТО, менеджер доходів) **документи бази знань** (36 статей) з поясненням шляхом у графі. Код: `reco/*`. Дані: `data/interactions/` (синтетичні, seed=42, див. `data/interactions/README.md`).

## 1. Підходи (C1)
| Підхід | Файл | Ідея | Холодний старт |
|---|---|---|---|
| Baseline: популярність | `reco/popularity.py` | сума ваг позитивних подій у train (open=1, save=2, helpful=2; view=0) | працює, однакове для всіх |
| Графовий | `reco/graph_reco.py` (Cypher: `reco/cypher.py`) | вага теми = α·роль + β·експозиція авіакомпанії до ризиків (шляхи через рейси) + γ·історія; оцінка документа = середня вага його тем | працює за роллю й авіакомпанією |
| Embeddings (kNN) | `reco/embed_reco.py` | вектор документа = середнє e5-векторів фрагментів; профіль користувача = зважена сума документів з історії; FAISS `IndexFlatIP` (косинус) | потребує історії; новий документ має вектор одразу |
| Гібрид | `reco/hybrid.py` | RRF або зважена сума min-max нормованих оцінок | успадковує |

Шляхи у графі (для пояснень, Результат 3):
- роль: `User -HAS_ROLE-> Role -FOCUSES_ON-> Topic <-ABOUT- Doc`
- експозиція: `User -WORKS_AT-> Airline <-OPERATED_BY- Flight -AFFECTED_BY-> Risk -RELEVANT_TO-> Topic <-ABOUT- Doc`
- історія: `User -OPENED-> Doc' -ABOUT-> Topic <-ABOUT- Doc`

## 2. Фільтри якості й прав (C2) — `reco/filters.py`
Застосовуються **до** ранжування (pre-filter). Причини відсіювання повертаються в `dropped`.
| Фільтр | Правило | Параметр |
|---|---|---|
| verified | лише `verified=true` | `FilterParams.require_verified` |
| свіжість | `last_reviewed` не старше 540 днів від `as_of` | `max_age_days` |
| права | `sensitivity` документа ≤ `access_level` користувача (public < internal < restricted) | `enforce_access` |
| доступність | `published_at ≤ as_of` | завжди |
| вже бачене | документи з позитивними подіями в train не рекомендуються | `exclude_seen` |

Демо: `make filters-demo` → `reports/filters_demo.txt` (3 користувачі з різними рівнями доступу; скрипт перевіряє, що відфільтрований документ не потрапляє у видачу). Тести: `tests/test_reco.py`.

## 3. Гібридне ранжування (C3) — `reco/config.py: HybridParams`
- `method`: `rrf` (за замовчуванням) або `weighted`.
- RRF: `score(d) = Σ_m w_m / (k + rank_m(d))`, `rrf_k = 60`.
- Ваги за замовчуванням: `graph=1.0, embed=1.0, pop=0.5` (початкові; **підбираються в Результаті 2** на валідаційній частині train, без використання test).
- Підхід без оцінок для користувача (напр. embeddings для нового користувача) просто не бере участі у злитті.

## 4. Відсутність витоку з майбутнього
Усі моделі навчаються лише на подіях `ts < cutoff` (`Dataset.train`); тест `test_train_has_no_future` це перевіряє. Деталі оцінювання — `docs/reco_eval.md` (Результат 2).

## 5. Обмеження (C4)
1. **Синтетичні дані.** Взаємодії згенеровано з тих самих сигналів (роль, ризики авіакомпанії), які використовує графовий підхід, тому він має «домашню перевагу»; результати не переносяться на реальних користувачів без перевірки.
2. **Малий каталог:** 36 документів і ~56 «теплих» користувачів; метрики мають широкі інтервали, coverage і novelty обмежені розміром каталогу.
3. **Ручна таксономія** (`reco/taxonomy.py`): теми документів і ролей призначено вручну (V1), помилка в ній напряму псує графовий підхід.
4. **Embeddings нечутливі до тем:** e5-вектори статей Вікіпедії дуже подібні між собою (косинус 0.97–0.99), тому kNN погано розрізняє документи; потрібне калібрування (центрування, ваги в гібриді).
5. **Метадані якості й права синтетичні:** `verified`, `last_reviewed`, `access_level` призначено для демонстрації фільтрів, а не отримано з реальних процесів.
6. **Немає онлайн-зворотного зв'язку:** модель статична, оновлюється повторним `fit`; позиційне зміщення кліків не моделюється.
