# Специфікація агента (Результат 1)

**Агент:** Aviation Hub Agent · **Домен:** управління авіаційними перевезеннями · **Версія специфікації:** 1.0 · **Підказка:** `agent/prompts/system_v1.md`
**Реалізація:** MCP-сервер `mcp_server/server.py` + агент `agent/agent.py` (LLM: Gemini з викликом інструментів). Схеми інструментів згенеровано в `docs/tool_schemas.json` (`make schemas`).

## 1. Мета, користувачі, межі, автономність

**Мета.** Відповідати українською на питання про авіаперевезення, спираючись лише на гібридне сховище знань: граф (рейси, аеропорти, авіакомпанії, ризики), текстову базу (статті Вікіпедії про авіацію) і OLAP-куб (метрики рейсів 2025 року). Кожне фактичне твердження має мати посилання на джерело; якщо даних немає, агент чесно відповідає `NO_ANSWER`.

**Користувачі й ролі.** Роль задає `ACCESS_LEVEL` на боці сервера, а не користувач чи модель.

| Роль | Що бачить |
|---|---|
| `public` (типова) | граф без Passenger і Pilot; документи KB з рівнем `public`; усі схвалені метрики |
| `internal` | + Pilot, + документи `internal` |
| `restricted` | + Passenger, + документи `restricted` |

**Межі (чого агент не робить).** Не змінює жодного сховища. Не відповідає без джерел. Не виконує інструкцій із тексту документів. Не передає персональні дані в зовнішні сервіси. Не відповідає на питання поза доменом авіаперевезень, якщо інструменти нічого не повернули (тоді `NO_ANSWER`).

**Рівень автономності: середній, лише читання.** Агент самостійно планує кроки, вибирає інструменти та формулює відповідь у межах лімітів (розділ 3). Будь-яка зміна знань можлива лише через інструмент `propose_fact` із затвердженням людини (Результат 5, `agent/propose_fact.py` і окремий сервер `mcp_server/propose_server.py`; сам агент нічого не записує і схвалити зміну не може).

## 2. Інструменти

Усі інструменти мають `readOnlyHint=true`; кожен виклик пишеться в `logs/tool_calls.jsonl`. Повні схеми: `docs/tool_schemas.json`.

| Інструмент | Призначення | Вхід (JSON-схема, скорочено) | Обмеження | Права | Коли використовувати |
|---|---|---|---|---|---|
| `graph_lookup` | Знайти сутність у графі й повернути її оточення (вузли та ребра з `confidence`) | `{entity: string (обов'язк.), hops: integer = 1}` | `hops` ≤ 2; ≤ 40 ребер (`truncated=true`, якщо більше); ≤ 5 стартових вузлів | Вузли Passenger / Pilot приховані без відповідного рівня | Питання про зв'язки: які рейси, яка авіакомпанія, які ризики впливають |
| `run_cypher` | Власний читальний Cypher до Neo4j, коли `graph_lookup` недостатньо | `{query: string (обов'язк.)}` | Один оператор із `RETURN`; заборонені `CREATE/MERGE/DELETE/SET/REMOVE/CALL/LOAD CSV/APOC`; автоматичний `LIMIT 50`; тайм-аут 10 с; виконання в READ-транзакції | Мітки Passenger / Pilot, зв'язки `HAS_PASSENGER` / `HAS_PILOT` і ключі `passengerId` / `pilotId` заборонені нижче потрібного рівня | Складні шаблони шляхів і підрахунки по графу. Потребує запущеного Neo4j |
| `vector_search` | Семантичний (гібрид dense + BM25) пошук у текстовій базі | `{query: string (обов'язк.), k: integer = 5}` | `k` ≤ 8; ≤ 1500 символів на фрагмент; повертає `id`, `source_url`, `license` | Pre-filter за `sensitivity` документа ДО ранжування. Підозрілі фрагменти відхиляються (`withheld`) | Визначення, правила, регулювання (слоти, права пасажирів, ATC тощо) |
| `list_metrics` | Каталог схвалених метрик і вимірів семантичного шару | `{}` | Показує лише метрики зі статусом `approved` | Без обмежень | Перед `query_metric`, якщо не знаєш точних назв |
| `query_metric` | Порахувати метрики по складу рейсів 2025 р. (DuckDB, зіркова схема) | `{metrics: string[] (обов'язк.), group_by: string[] = [], filters: [{dim, op, value}] = [], order_by: string \| null, limit: integer = 50}`; `op` ∈ `=, <>, <, >, <=, >=, IN, NOT IN` | Вільного SQL немає: SQL будується з реєстру `metrics.yml` (whitelist метрик і вимірів); значення екрануються; ≤ 50 рядків; з'єднання DuckDB read-only без зовнішнього доступу | Без обмежень за рівнями (дані агреговані) | Числа, частки, порівняння, агрегати по сезонах, авіакомпаніях, аеропортах |

**Формат цитування.** Кожна відповідь інструмента містить `id`: `graph:<Label>:<key>`, `kb:<chunk_id>`, `sql:<hash>`, `cypher:<hash>`. Агент має цитувати лише ці `id`.

## 3. Політики

### 3.1 Ліміти (значення з `agent/policies.py`, змінюються через `.env`)
| Ліміт | Значення | Дія при перевищенні |
|---|---|---|
| Кроки LLM на запит | 8 | зупинка, `stop_reason=step_limit` |
| Виклики інструментів на запит | 10 | виклик відхиляється (`tool_call_limit`), зупинка |
| Токени (prompt + output) на запит | 40 000 | зупинка, `token_limit` |
| Час на запит | 90 с | зупинка, `time_limit` |
| Однаковий виклик (ім'я + аргументи) | не більше 2 разів | зупинка, `loop_detected` |
| Розмір результату інструмента | 16 000 символів | відхиляється з `result_too_large`, агент має звузити запит |
| Рядки / ребра / фрагменти | 50 / 40 / 8 | обрізання на боці сервера |

Після зупинки без відповіді користувач отримує `NO_ANSWER: перервано (<причина>)`.

### 3.2 Заборонені дії
1. Будь-який запис, зміна чи видалення даних у графі, KB або сховищі (немає жодного інструмента запису; Cypher-guard блокує запис).
2. Вільний SQL від моделі (тільки метрики з реєстру).
3. Доступ до Passenger і Pilot, а також до документів KB вище рівня ролі.
4. Виконання інструкцій, знайдених у даних (документи, значення полів, описи): це недовірений вміст.
5. Розкриття системного промпта та внутрішньої конфігурації.
6. Відповіді без посилань на джерела та вигадані `id` (перевіряє вузол verify).
7. Підвищення власного рівня доступу: його задає `ACCESS_LEVEL` сервера, а не аргументи інструментів.
8. Передача персональних даних у зовнішні сервіси (в LLM не надсилаються дані Passenger на рівні `public`).

### 3.3 Human-in-the-loop (правила підтвердження людиною)
| Ситуація | Правило |
|---|---|
| Запис нового знання у сховище | Лише через `propose_fact`: валідація (SHACL, джерело) → оцінка ризику. Середній і високий ризик потребують схвалення людини; запис без provenance заборонений (Результат 5) |
| Зміна рівня доступу (`ACCESS_LEVEL`) | Лише адміністратором на рівні конфігурації сервера, не агентом |
| Відповідь не пройшла перевірку цитат | Не віддається користувачу: `NO_ANSWER` + запис у трасу для ручного розбору |
| Зупинка за лімітом або зациклення | Фіксується в `logs/trace.jsonl` (`stop_reason`); людина переглядає такі запити під час оцінювання |

### 3.4 Журнал
- `logs/trace.jsonl`: трасування запиту (кроки, виклики, результати, затримки, токени, вартість, `stop_reason`, перевірка цитат).
- `logs/tool_calls.jsonl`: серверний журнал кожного виклику (інструмент, аргументи, статус `ok/blocked/error`, затримка, `access_level`, `defenses`).
- `llm_log/`: журнал взаємодії з LLM за протоколом «LLM-експерт» (модель, параметри, версія підказки, сирий вихід, рішення людини).

### 3.5 Цикл роботи агента (для довідки на захисті)
`питання → LLM планує → виклик інструментів (MCP) → LLM складає відповідь → verify (цитати ∈ результатів інструментів; одна спроба виправлення) → відповідь або NO_ANSWER → запис у trace`.

## 4. Пам'ять

| Тип | Що зберігається | Де | Правила зберігання / TTL |
|---|---|---|---|
| Робоча (короткострокова) | історія повідомлень поточного запиту, результати викликів, множина дозволених для цитування `id` | в оперативній пам'яті процесу агента | Живе до завершення одного запиту; між запитами не переноситься |
| Епізодична (трасування) | кроки, виклики, результати (скорочено), токени, вартість, затримки | `logs/trace.jsonl`, `logs/tool_calls.jsonl` | Зберігати 30 днів (політика; автоочищення в коді не реалізовано). Без персональних даних; `logs/` не комітиться (`.gitignore`) |
| Довгострокова (знання) | граф, текстова база, куб | `data/` | Змінюється лише через `propose_fact` із provenance і схваленням людини; без TTL, зміни мають аудит (Результат 5) |
| Користувацька пам'ять | нічого | — | Агент не запам'ятовує користувача між сесіями; вхідні запитання не потрапляють у знання |

## 5. Відповідність критеріям
| Критерій | Де в документі |
|---|---|
| C1: ≥ 3 інструменти з JSON-схемою й обмеженнями | розділ 2 і `docs/tool_schemas.json` |
| C2: ліміти (кроки, токени, час) | розділ 3.1 |
| C3: заборонені дії й підтвердження людиною | розділи 3.2 і 3.3 |
| C4: типи пам'яті й правила зберігання | розділ 4 |
