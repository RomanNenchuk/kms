# СР 9 — Критерії порівняння графових баз (Neo4j · GraphDB · Memgraph)

Тема: **управління авіаційними перевезеннями**. Датасет: 892 вузли (60 аеропортів, 12 авіакомпаній,
120 літаків, 700 рейсів), ≈3400 ребер, 5 запитів Q1–Q5.

## Що де працює

| Що | Де | Чому |
|---|---|---|
| Neo4j, Memgraph, GraphDB | Docker Compose | три різні стеки (JVM / C++ in-memory / JVM + RDF), без Docker довелося б ставити кожен руками |
| Python-скрипти (генератор, loader, bench) | `.venv` на хості | швидше правити й запускати, підключаються до портів контейнерів |

Порти: Neo4j Browser `7474`, Neo4j Bolt `7687`, Memgraph Bolt `7688`, GraphDB Workbench `7200`.
Усім трьом виділено ~1 ГБ пам'яті, щоб порівняння було чесним.

## Запуск

```bash
make venv          # .venv + neo4j, requests
make up            # docker compose up -d (перший pull займе кілька хвилин)
docker compose ps  # дочекатися (healthy) у всіх трьох
make data          # data/*.csv, data/avia.ttl, data/oracle.json
make load          # завантаження в усі три сховища -> results/load.json
make bench         # Q1–Q5 × 3 бази -> results/results.json, results/report_tables.md
```

`make check` — офлайн-перевірка SPARQL-запитів (rdflib) без Docker.

## Як влаштована перевірка еквівалентності (C2)

`gen_data.py` рахує правильні відповіді Q1–Q5 чистим Python (`data/oracle.json`). `bench.py` порівнює
результат кожного сховища з цим еталоном рядок у рядок (у т.ч. порядок). Якщо щось розійшлося, це
потрапляє в окремий блок «Розбіжності» у `report_tables.md`, і його треба пояснити у звіті.

## Що вже перевірено, а що ні

- ✅ SPARQL-запити збігаються з оракулом на `rdflib` (усі 5).
- ✅ Генератор, логіка `bench.py` і формування таблиць (dry-run із фейковими бекендами), `docker compose config`.
- ⚠️ Cypher-запити та loader для Neo4j/Memgraph, REST-виклики GraphDB **ще не запускались на реальних
  серверах** (образи не завантажуються з середовища, де я збирав проєкт). Перший `make load`/`make bench`
  і є справжньою перевіркою. Якщо щось впаде, скинь текст помилки.

## Обмеження бенчмарка (для відповіді на питання 3 самоперевірки)

- Малий датасет (≈900 вузлів): усе вміщується в кеш, різниці між індексами/плануванням майже не видно.
- Час клієнтський (включає мережу й серіалізацію), а не серверний профіль.
- 20 замірів після 3 прогрівальних; одна машина, контейнери ділять CPU.
- Синтетичний розклад: літак може «бути в двох місцях одночасно», реальних обмежень немає.
- У RDF немає `distance_km` на ребрі `route` (для цього потрібен RDF-star або reification); Q1–Q5 цей атрибут не використовують.
- Q4 у SPARQL розгорнуто як `route | route/route | route/route/route`, бо `{1,3}` немає в SPARQL 1.1.

## Звіт

`report/REPORT_TEMPLATE.md`: каркас під вимоги викладача (таблиця 8 критеріїв, таблиця часу/зручності/
обмежень, рекомендація, декларація ШІ). Таблицю критеріїв заповнено **чернеткою**, її треба звірити з
документацією кожного сховища й додати посилання.
